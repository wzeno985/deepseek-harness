# Agent Note: fork 在提交前拦截密钥

Status: implemented

[English](2026-10-30-fork-secret-gate-before-commit.md) | 中文

## 问题

仓库没有任何机械化的密钥门禁。[pre-commit hooks](../../../../lefthook.yml) 只校验配对记录、已归档笔记、lint、空白、pi-ai 元数据与 vendor 清单，而 [run-gates.ts](../../../../scripts/run-gates.ts) 里的 CI 门禁清单完全不包含凭据检查。今天保护凭据的是流程：`.gitignore` 挡住 `.env` 与两个桌面环境文件，项目说明禁止提交凭据，审查者人工留意。

这套做法默认了一个私有的审查闭环。本 fork 是公开的，且它的 CI 只运行静态门禁集，因此在暂存文件与公开提交之间，没有任何环节检查内容是否含凭据。GitHub 自带的 secret scanning 只覆盖服务商可识别的模式；能覆盖通用 token 形状的 non-provider 设置在本次仓库处于关闭状态，且只能通过网页设置开启，无法通过 REST API 修改。

## 决策

`scripts/check-staged-secrets.sh` 作为 `pre-commit` job 运行，扫描暂存内容中形如凭据的字符串：服务商风格的 token 前缀、私钥装甲块，以及 `DEEPSEEK_API_KEY=` 后接长值这类赋值形式。它通过 `git grep --cached` 读取索引，因此判断的正是提交将包含的内容；命中时按文件与行各报告一条掩码后的行，然后让提交失败。

两个逃生口让门禁保持可用：

- **fixture 白名单。** 有两个产品测试断言形如凭据的输入如何被掩码与回显，因此它们的精确 fixture 值被列入脚本白名单。这些值在脚本里由多段拼合而成，因为直接写出的长 token 会让脚本触发自己的扫描。
- **行内标记。** 任意行都可以带 `secret-scan: allow`，在审查者会读到的地方声明这是刻意的 fixture 或文档示例。

脚本刻意只报告它认识的那些形状。它是对误提交的检查点，而不是"该文件不含凭据"的判定。

## 曾考虑的替代方案

- **只依赖 GitHub secret scanning。** 否决：只覆盖服务商模式，non-provider 设置处于关闭状态且无法通过 API 开启，而且告警到达时提交已经推送到公开仓库。
- **引入 gitleaks 或 detect-secrets。** 暂时否决：两者都带来依赖、配置文件与持续更新义务，而本 fork 的内容改动只有文档与 CI，此处相关的形状少且稳定。
- **在 CI 而非 hook 里强制扫描。** 否决：本 fork 的快速 lane 运行静态验证脚本，CI 检查会把信号推迟数分钟，且在此期间内容仍会到达公开远端。
- **按路径白名单整个 fixture 文件。** 否决：路径白名单会悄悄削弱这些文件未来每一行的保护，而值白名单与行内标记让每个例外都保持可见。

## 后果

换来的是：形如凭据的内容在成为提交之前被拦下，检查读取索引而非工作树，并且每个例外都出现在引入或使用它的 diff 里，可见可审。

代价是：当出现新的重要凭据格式时需要扩展模式列表；fixture 或文档里的长随机串会让提交失败直到被标记；门禁看不到已经提交的值，因此早于它的泄露仍然只能靠轮换解决。

## 测试

- 落地前对四种暂存情形做了实测：脚本自身、含 key 形状赋值语句的暂存文件、仓库的两个 fixture 文件、以及带行内标记的行。第一、第三、第四种通过；第二种报告一条掩码行并以非零码退出。
